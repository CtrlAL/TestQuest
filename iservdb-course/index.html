01

Что это за проект

ISERVDB — это «бухгалтерия» коммунальной службы, написанная на SQL

Представь себе расчётный отдел ЖКХ

Перед тобой — база данных под названием ISERVDB. В ней живёт учёт одной коммунальной службы: кто сколько должен за свет и воду, кто заплатил, какие счётчики стоят у людей дома.

Это не приложение с кнопками, которые ты нажимаешь. Это «мозг» такого приложения — набор правил на языке SQL, который умеет отвечать на вопросы вроде «сколько Иванов должен на 1 марта?».

💡
Зачем тебе это знать

Ты можешь попросить ИИ написать такой «мозг» для своего проекта. Чтобы он сделал это хорошо, ты должен понимать, из каких частей тот состоит и зачем каждая нужна.

Что умеет этот «расчётный отдел»

Задание для разработчика звучало так: написать набор функций, которые отвечают на типичные вопросы диспетчера ЖКХ:

📊

Долги по срокам

Сколько клиент должен «свеженького» (до 30 дней) и сколько уже просрочено на месяцы.

📅

Долги по месяцам

Сводка начислений и долгов за выбранный год, с детализацией или без.

📋

Документы и дела

Какие «мероприятия» (звонки, иски) открыты по документу и всей его цепочке.

⚡

Расход по счётчикам

Сколько электричества накрутил счётчик и на какую сумму это выльется.

02

Кто здесь живёт

Таблицы базы — это папки, каждая про свой вид данных

Шкаф с папками

Представь таблицу как отдельную папку в расчётном отделе. В папке «Лицевые счета» лежат люди, в папке «Счета» — выставленные квитанции, в папке «Тарифы» — цены. База ISERVDB — это набор таких папок, которые постоянно сверяют друг с другом.

🗂️
Полезный термин

Связь между папками держится на ключах: у каждого клиента есть свой номер, и по нему счета «привязаны» к человеку.

03

Как детали общаются

JOIN склеивает папки по общему ключу — как сверка двух ведомостей

Что такое JOIN

Чтобы собрать отчёт, базе нужно соединить людей со их счетами. Операция JOIN берёт строки из одной папки и приклеивает к ним подходящие строки из другой.

Метафора: у тебя две тетради — в одной имена учеников, в другой их оценки. По «номеру ученика» ты подписываешь каждой оценке нужное имя. Результат — одна таблица «имя + оценка».

Путь одного запроса

Нажми «Следующий шаг», чтобы проследить, как данные ползут между таблицами при вызове отчёта о долгах:

Код склейки, слово в слово

Вот реальный кусок из функции rpt_subscrs_debts_by_term — именно он соединяет клиента со счетами:

CODE 
FROM dbo.sd_subscrs s
JOIN dbo.fd_bills b ON b.f_subscr = s.link
WHERE s.link = _f_subscr
  AND b.d_date <= _d_date
PLAIN ENGLISH

Начинаем с папки лицевых счетов (назовём её буквой s).

Приклеиваем к каждому счёту (b) строку, где владелец счёта совпадает с клиентом.

Оставляем только того клиента, которого попросили.

И только счета, выписанные не позже указанной даты.

💡
Ключевая мысль

JOIN — это не «слияние двух таблиц в одну навсегда», а взгляд на них рядом, только на время одного запроса. Исходные папки не меняются.

Junior: четыре отчёта

Как четыре функции превращают сырые таблицы в понятные отчёты

Что сдал джуниор

Задание Junior — написать четыре отчётные функции. Все они на чистом SQL: берут данные, считают и возвращают таблицу. Никакой логики «в цикле» — только умные запросы.

📊

debts_by_term

Долги по «возрасту»: свежие, постарше, совсем старые.

📅

debts_by_year

Сводка по месяцам года, с детализацией или без.

📋

subscrs_docs

Дела и мероприятия по документу и всей его цепочке.

⚡

subscrs_quantity

Расход по счётчику и сумма к оплате по тарифу.

Долги по срокам: корзины через CASE

Функция debts_by_term раскладывает каждый счёт по трём «корзинам» в зависимости от того, сколько дней прошло. Для этого используется CASE — переключатель прямо внутри суммы:

CODE 
SUM(CASE WHEN _d_date - b.d_date BETWEEN 0 AND 30
             THEN b.n_amount ELSE 0 END)::numeric(19, 4) AS "Нач. до 30 дней"
PLAIN ENGLISH

Сложи суммы, но не все подряд…

…только те счета, где разница дат — от 0 до 30 дней.

Остальные считаем за 0, чтобы не попали в эту колонку.

Результат подпишем «Начислено до 30 дней».

Таких блоков три — для корзин «до 30», «31–180» и «старше 181 дня». Всё считается за один проход по таблице.

Сводка по году: переключатель детализации

Функция debts_by_year умеет работать в двух режимах — один и тот же запрос, но с флагом _b_detail. Если он включен, добавляется колонка «Услуга»:

CODE 
CASE WHEN _b_detail THEN b.c_sale_items ELSE NULL END AS "Услуга",
to_char(b.d_date, 'MM.YYYY') AS "Месяц"
PLAIN ENGLISH

Хочешь детализацию — покажи название услуги, нет — оставь пусто.

Дату счёта преврати в удобный вид «месяц.год», например 03.2020.

🎛️
Один код — два отчёта

Вместо двух разных функций джуниор сделал одну с переключателем. Меньше дублирования — проще поддерживать.

Документы: рекурсивное дерево

Документы могут ссылаться друг на друга — «родитель → потомок». Чтобы собрать цепочку, функция subscrs_docs использует рекурсивный CTE — запрос, который сам себя повторяет, пока не выберет всё дерево:

CODE 
WITH RECURSIVE doc_tree AS (
    SELECT d.link, d.f_subscr FROM dbo.dd_docs d
    WHERE d.link = _f_docs
  UNION ALL
    SELECT p.link, p.f_subscr FROM dbo.dd_docs p
    JOIN doc_tree t ON p.f_docs = t.link
)
PLAIN ENGLISH

Начни с конкретного документа, который попросили.

Затем на каждом круге ищи документы, чей «родитель» — уже найденный.

Повторяй, пока цепочка не закончится.

Собери всё в одну временную табличку doc_tree.

Счётчики: оконные функции

Функция subscrs_quantity считает расход между двумя показаниями и среднее за год. Для этого — оконные функции. Они смотрят на «соседей» строки, не сливая всё в кучу:

CODE 
ROW_NUMBER() OVER (
  PARTITION BY r.f_devices ORDER BY r.d_date DESC) AS rn

r.n_value - LAG(r.n_value) OVER (
  PARTITION BY r.f_devices ORDER BY r.d_date) AS cons
PLAIN ENGLISH

Пронумеруй показания каждого прибора, свежие первыми (номер 1 — самое последнее).

Расход = текущее значение минус предыдущее (LAG подсматривает строку выше).

PARTITION BY значит «считай отдельно для каждого прибора».

💡
Почему это круто

Оконные функции решают задачу «сравнить строку с соседней» без циклов и без дублирования запросов. Это главный признак зрелого SQL-кода.

05

Middle: распределение платежа

Одна функция раскладывает сумму платежа по счетам клиента

Задача посложнее

Клиент принёс платёж — допустим, 400 рублей. Но у него несколько счетов: за свет, воду, отопление, да ещё с долгами за разные месяцы. Надо понять, какую часть долга какого счёта этот платёж закрывает. Функция ui_fp_payment_split делает это сама.

В отличие от отчётов Junior, здесь код не на чистом SQL, а на PL/pgSQL — то есть можно использовать переменные и циклы, как в обычной программе.

Тип 0: гасим самые старые счета первыми

Первый режим работает по принципу FIFO: сначала закрываем самый старый долг, потом следующий, пока деньги не кончатся.

1
Берём сумму платежа

Допустим, у нас в руках 400 рублей к распределению.

2
Идём по счетам от старых к новым

Счёт от декабря 2018, потом январь 2019, и так далее.

3
Гасим сколько влезает

Списываем с текущего счёта минимум из «остаток платежа» и «долг по счёту».

4
Повторяем, пока деньги есть

Как только платёж исчерпан — останавливаемся.

Тип 1: делим пропорционально услугам

Второй режим хитрее: внутри одного месяца платёж распределяется между услугами пропорционально их доле в долге. Вот реальный кусок цикла по услугам:

CODE 
FOR _service_name, _service_rest IN
    SELECT b.c_sale_items, SUM(b.n_amount_rest)
    FROM dbo.fd_bills b WHERE ...
    GROUP BY b.c_sale_items ORDER BY b.c_sale_items
LOOP
    _service_payment := ROUND(
      _remaining * _service_rest / _month_total, 4);
END LOOP;
PLAIN ENGLISH

Для каждой услуги месяца (свет, вода…) возьми её остаток долга.

Сгруппируй одинаковые услуги и сложи их долги.

Доли: доля услуги = платёж × (её долг ÷ общий долг месяца).

Округляем до 4 знаков, чтобы копейки сошлись.

💡
Пропорция — это честность

Если платежа не хватает на весь месяц, пропорциональное деление гасит каждую услугу «по справедливости», а не зануляет одну и игнорирует остальные.

Защита от повторного запуска

Что если функцию вызовут дважды для одного платежа? Без защиты деньги распределились бы второй раз и «сожгли» бы долги повторно. Поэтому в самом начале стоит страж:

CODE 
IF EXISTS (
  SELECT 1 FROM dbo.fd_payment_details
  WHERE f_payments = _link
) THEN
  RETURN;
END IF;
PLAIN ENGLISH

Если для этого платежа детализация уже создана…

…просто выйди и ничего не меняй.

⚠️
Идемпотентность

Свойство операции срабатывать один раз независимо от числа вызовов. Без этой проверки повторный запуск исказил бы остатки долгов — классический баг в платёжных системах.

06

Когда всё ломается

Где прячутся ошибки и как устроена база в целом

Крайние случаи, о которых думает профи

Реальные данные редко идеальны. Хороший разработчик заранее учитывает ситуации, когда «всё пошло не по плану»:

0️⃣

Нулевой платёж

Сумма 0 — функция должна просто ничего не делать, а не падать.

💰

Переплата

Платёж больше всего долга — остаток «сгорает», счета обнуляются.

📆

Дата в будущем

Показания и счета отсекаются условием «не позже даты» — иначе будет пусто.

CODE 
IF NOT FOUND OR _payment_amount <= 0 THEN
  RETURN;
END IF;
PLAIN ENGLISH

Если платёж не найден в базе…

…или его сумма ноль либо меньше — выйти, ничего не трогая.

Отладка: куда смотреть

Допустим, отчёт показывает пустоту или не ту сумму. Вот куда идти проверять — по порядку:

1
Параметры

Точно ли передан правильный номер клиента и дата? Частая ошибка — перепутан порядок.

2
Исходные таблицы

Есть ли вообще счета у этого клиента на нужную дату? SELECT из fd_bills напрямую.

3
Условия JOIN и WHERE

Не отсекает ли фильтр по дате лишнее? Не теряются ли строки из-за строгого равенства.

4
Детали расчёта

Корректны ли корзины CASE и округления? Сверь с эталонным результатом из задания.

Большая картина: Junior против Middle

Два уровня задания показывают, как растёт ответственность кода:

CODE 
-- Junior: только читает и считает
CREATE FUNCTION ... RETURNS TABLE (...)
  LANGUAGE sql  -- SELECT, ничего не меняет

-- Middle: меняет данные
CREATE FUNCTION ... RETURNS void
  LANGUAGE plpgsql -- INSERT/UPDATE счетов
PLAIN ENGLISH

Junior-функции только показывают данные — база не меняется.

Они возвращают таблицу, как справку.

Middle-функция сама правит остатки долгов в базе.

Ответственность выше: ошибка испортит реальные данные.

💡
Главный урок

Чем больше код меняет данные, тем важнее защиты (проверки, идемпотентность). Отчёты можно перезапустить сколько угодно — изменения базы необратимы.
